# Recording storage and export format (version 1)

Audio and metadata live in the app's private no-backup `recordings` directory. Uninstalling the app or clearing its storage removes them, so export originals regularly. The app does not delete or overwrite old recordings. When cloud backup is connected and enabled, it also uploads committed recordings and their metadata to the selected cloud accounts. Device loss, storage failure, and interrupted power can still lose data.

Each recording segment has an immutable ASCII basename containing a validated session identifier, segment index, and starting device wall-clock timestamp. Capture writes AAC-LC frames in an ADTS stream to `.aac.partial`. The recording engine requests 48 kHz, mono, 64 kbit/s. Once the caller has closed the file, storage syncs and renames it to `.aac` for a clean finalization, or `.interrupted.aac` following an interruption. A truncated last ADTS frame can remain after a crash; recovery preserves original bytes rather than editing them.

`<stem>.open.json` records the requested segment start and is preserved. `<audio filename>.json` records the finalized file basename, byte size, SHA-256, status, start/end epoch and monotonic times, wall/monotonic clock offsets, and AAC frame count duration at the nominal sample rate. The recording engine derives segment timestamps from the session device-clock origin and encoded frame counts; these estimates do not establish exact real-world capture endpoints, capture loss, or later wall-clock adjustments. Monotonic timestamps have meaning only within the same device boot. Interrupted recovery does not invent the last captured sample time: unknown end times and duration are null. Missing or damaged opening metadata is explicitly reported. Requested codec parameters describe the recording configuration, rather than independently proving the contents of a damaged stream.

`events.jsonl` is an append-only, synced event journal. A sudden interruption can leave an incomplete final line. The next event begins on a new line without removing that damaged record. JSON metadata is written and synced to a unique temporary file before rename; uncommitted temporary files remain available for inspection if a write fails. Rename and sync improve resilience but cannot guarantee survival through all power or flash-storage failures.

Newly finalized segments also contain an optional `journal_snapshot` object in their sidecar. It names an immutable `<audio filename>.events-<start>-<end>.jsonl` file, declares `source: "events.jsonl"`, and stores `start_byte`, `end_byte`, `size_bytes`, and `sha256`. The range includes the start byte and excludes the end byte. Its bytes are preserved exactly, including any incomplete event line. A cursor advances only after the snapshot and segment sidecar commit. Recovery may therefore produce overlapping ranges; duplicates are permitted and preserve events after an interrupted cursor update. Background sync also seals trailing stop/error events as standalone `journal_<UUID>.events.jsonl` checkpoint bundles. Checkpoint files are not separately added to ZIP exports because their bytes already appear in the exported full journal prefix.

When opening metadata exists at finalization, new sidecars contain `opening_metadata_size_bytes` and `opening_metadata_sha256`. The referenced file is `<stem>.open.json`, where `<stem>` removes either `.aac` or `.interrupted.aac` from the audio filename. This hash covers the original opening file even if it contains damaged JSON; the sidecar separately reports the parsing error. These fields and `journal_snapshot` are optional additions to format version 1, so older recordings remain supported.

ZIP export snapshots finalized files with committed sidecars and a fixed byte prefix of the journal. It also includes their opening metadata and referenced journal deltas, when present. Only directory enumeration and journal-prefix capture hold the store lock; immutable metadata scanning and bulk copying run outside it so recording can continue. Active `.partial` files, finalized audio lacking a committed sidecar, and temporary metadata are excluded. `export_metadata.json` reports excluded partial recordings and incomplete finalizations. Therefore an export can omit the currently active segment; stop recording before export if every captured segment is needed. A new user start recovers stale partial files and finals missing sidecars while no recording engine is active.

ZIP members are `recordings/<basename>`, `events.jsonl` when available, `export_metadata.json`, and `SHA256SUMS`. Each line of `SHA256SUMS` is 64 lowercase hexadecimal SHA-256 characters, two spaces, the ZIP-relative path, and a newline. It covers every member except `SHA256SUMS` itself. The ZIP contains no directory entries. Export does not alter recordings. A failed export can leave an incomplete ZIP at the chosen destination; retry to a new destination after resolving the reported failure.

Run `python tools/verify_export.py path/to/export.zip` to validate safe and unique ZIP paths, exact manifest coverage, every payload hash, segment counts, and audio sidecar consistency. When optional references are present, it also checks opening metadata size/hash, journal snapshot size/hash, byte-range bounds, and exact agreement with the referenced range of `events.jsonl`. It accepts overlapping journal ranges and legacy sidecars without the new fields. The script reads the archive without extracting or modifying it; journal-range comparisons stream the source once rather than repeatedly rereading large prefixes. Run `python -m unittest discover -s tools -p test_verify_export.py` for its tests.

App version 1.2 also offers **Export individual files to folder**. The signed 1.2 APK is ready but has not been installed or tested with the handset's folder provider. This option writes committed audio and sidecars under their original basenames, together with referenced opening metadata and event deltas/checkpoints. It attempts to seal trailing journal events before selecting bundles, and reports failures while allowing unaffected bundles to copy. Active audio is excluded. Existing identical destination files are read and hash-checked, then reused. Differing or ambiguous names remain untouched and are reported. New files are written with a unique `Pending_...` name, read back, then renamed and checked again; incomplete copies remain available for inspection. The destination must support rename. Do not use concurrent external writers in that folder, because Android document-provider rename is not an atomic no-replace operation.

Each individual-folder run creates `SHA256SUMS_<epoch>_<UUID>.txt`, containing standard `sha256  basename` lines for all files in fully verified bundles from that run. It does not claim coverage of other manifests, incomplete `Pending_...` copies, conflicting bundles, or unrelated destination files. The folder has no full root `events.jsonl` or ZIP `export_metadata.json`: a sidecar's `journal_snapshot.source` identifies the original app journal, and its delta preserves only the declared byte range. Folder manifests therefore check copied bytes but do not provide the full ZIP journal-range validation. `tools/verify_export.py` expects a ZIP, not this directory format.

For a dated directory that retains every member of a verified ZIP, use Python 3.9 or later:

```powershell
python tools/organize_export.py C:\path\to\export.zip C:\path\to\new-individual-files
```

The output and its sibling `.filelist.json` must not exist; their parent directories must exist. The organizer verifies the original ZIP and every copy, keeps original member bytes unchanged, and arranges audio plus its metadata under `audio/YYYY-MM-DD/` using recorded UTC start dates. Invalid/missing dates use `audio/undated/`. Root `events.jsonl` and `export_metadata.json` are preserved, while the original `SHA256SUMS` moves unchanged to `records/original-export/SHA256SUMS` and still refers to ZIP paths. `SHA256SUMS.csv` maps old paths to new paths and hashes every output except itself; the sibling file-list report includes that CSV too. Generated indexes and `ORGANIZATION.json` aid navigation and record the original archive hash. This rearrangement does not certify timestamps or analyze audio; filesystem copy times are not recording times. An optional `--expected-sha256` argument checks a previously recorded trusted ZIP digest.

SHA-256 provides a later byte comparison, not authentication. Someone able to replace the archive can also replace its hashes. These files do not independently establish speaker identity, truthful timestamps, continuous capture, an unmodified device, chain of custody, or legal admissibility. Preserve exported ZIPs unchanged and let your lawyer decide how to document receipt and retain independent copies.
